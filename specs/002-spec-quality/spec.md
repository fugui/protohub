## 用户场景与测试 *(必填)*

### 用户故事 1 - API 文档错误修正 (优先级: P1)

技术团队在执行代码审查和实现时，发现 OpenAPI 规范文档中的引用错误，需要修正以确保文档准确性。

**为什么是此优先级**: API 文档错误会导致前后端集成时的混淆和潜在实现错误，必须先修正才能继续开发。错误的引用会阻碍代码生成工具的正常工作。

**独立测试**: 可以通过验证 OpenAPI 规范文件的语法正确性和引用完整性来独立测试。使用 OpenAPI 验证工具（如 swagger-cli validate）验证文档无错误。

**验收场景**:

1. **给定** 用户运行 OpenAPI 验证工具检查 api.yaml，**当** 工具执行验证，**那么** 工具报告验证通过，无引用错误
2. **给定** 用户在 api.yaml 中查找所有 $ref 引用，**当** 检查每个引用路径，**那么** 所有引用都指向有效的组件路径（如 '#/components/schemas/User'）
3. **给定** 开发人员基于 api.yaml 生成客户端代码，**当** 代码生成工具解析文档，**那么** 工具成功生成代码，无引用错误

---

### 用户故事 2 - 任务列表清理 (优先级: P1)

开发人员在执行开发任务时，发现任务列表中存在重复和编号混乱的任务，需要清理以确保任务执行的清晰性。

**为什么是此优先级**: 重复和编号混乱的任务会导致开发人员困惑，可能执行重复工作或遗漏任务。必须先修正才能确保实施阶段的正确性。

**独立测试**: 可以通过检查任务列表的唯一性和编号连续性来独立验证。每个任务 ID 应唯一且无重复，编号应连续无跳过。

**验收场景**:

1. **给定** 用户查看 tasks.md 文件，**当** 检查任务编号，**那么** 任务编号从 T001 到 T105 连续，无跳过或重复
2. **给定** 用户搜索 tasks.md 中的所有任务描述，**当** 检查重复内容，**那么** 没有两个任务具有相同的描述和责任范围
3. **给定** 用户查看词汇管理相关任务（T078-T083），**当** 检查任务列表，**那么** 每个任务职责清晰，无重复定义

---

### 用户故事 3 - 通知渠道明确化 (优先级: P2)

系统用户（开发人员、审核员）需要明确系统如何发送审核结果通知，以便正确配置和使用通知功能。

**为什么是此优先级**: 明确通知渠道对于用户体验和功能配置很重要，但不会阻碍核心功能的开发和测试。可以在实现阶段灵活调整。

**独立测试**: 可以通过模拟审核流程并验证通知发送方式来独立测试。系统应根据配置的通知渠道发送通知。

**验收场景**:

1. **给定** 审核员批准了一个文件变更，**当** 系统处理审核结果，**那么** 系统通过配置的通知渠道（邮件或应用内通知）向提交人发送通知
2. **给定** 审核员拒绝了一个文件变更并填写拒绝理由，**当** 系统处理审核结果，**那么** 系统通过配置的通知渠道向提交人发送包含拒绝理由的详细通知
3. **给定** 系统配置了邮件通知，**当** 审核结果产生，**那么** 提交人收到包含文件信息、审核状态和审核意见的电子邮件
4. **给定** 系统配置了应用内通知，**当** 用户登录系统，**那么** 用户在通知中心看到待读的审核结果通知

### 用户故事 4 - 单元测试覆盖增强 (优先级: P1)

技术团队需要确保核心服务模块有足够的单元测试覆盖，以满足项目宪法规定的 80% 测试覆盖率要求。

**为什么是此优先级**: 项目宪法明确要求核心业务逻辑必须有 80% 以上的单元测试覆盖率。测试任务缺失会导致合规性问题和代码质量风险。

**独立测试**: 可以通过执行测试覆盖率工具（如 Jest 覆盖率报告）来独立验证每个服务模块的测试覆盖率。

**验收场景**:

1. **给定** 用户运行 fileService 的单元测试套件，**当** 测试完成并生成覆盖率报告，**那么** 报告显示覆盖率不低于 80%
2. **给定** 用户运行 reviewService 的单元测试套件，**当** 测试完成并生成覆盖率报告，**那么** 报告显示覆盖率不低于 80%
3. **给定** 用户运行 gitService 的单元测试套件，**当** 测试完成并生成覆盖率报告，**那么** 报告显示覆盖率不低于 80%
4. **给定** 用户运行 dependencyService 的单元测试套件，**当** 测试完成并生成覆盖率报告，**那么** 报告显示覆盖率不低于 80%
5. **给定** 用户运行 consistencyService 的单元测试套件，**当** 测试完成并生成覆盖率报告，**那么** 报告显示覆盖率不低于 80%
6. **给定** 用户执行完整的测试套件，**当** 所有测试通过，**那么** 整体核心业务逻辑覆盖率不低于 80%

### 边界情况

- 如果 OpenAPI 文档中存在多个相同的引用错误，如何批量修正？
- 任务重新编号后，如何确保依赖关系（如 T033 依赖 T012）仍然正确？
- 如果用户同时配置了邮件和应用内通知，系统是否同时发送两种通知？
- 如果通知渠道配置错误（如邮件服务器不可达），系统如何处理通知失败？
- 某些服务模块可能只有少量业务逻辑，是否仍需达到 80% 测试覆盖率？
- 如果服务模块的单元测试无法覆盖某些边界条件（如外部依赖失败），如何计算覆盖率？

## 需求 *(必填)*

### 功能需求

#### API 文档修正

- **FR-001**: 系统必须确保 OpenAPI 规范文档中的所有 $ref 引用路径正确，指向有效的组件定义
- **FR-002**: OpenAPI 文档中的 schema 引用必须使用完整路径 '#/components/schemas/{schema_name}'
- **FR-003**: OpenAPI 文档必须通过标准验证工具（如 swagger-cli validate）验证，无错误和警告

#### 任务列表清理

- **FR-004**: 任务列表中的每个任务 ID 必须唯一，无重复
- **FR-005**: 任务编号必须从 T001 开始连续递增，无跳过
- **FR-006**: 词汇管理相关任务（原 T078-T083）必须去重，每个任务职责明确且不重叠
- **FR-007**: 任务依赖关系必须保持一致，重新编号后不影响依赖引用的正确性

#### 通知渠道明确化

- **FR-008**: 系统必须支持邮件通知渠道，通过 SMTP 服务器发送审核结果
- **FR-009**: 系统必须支持应用内通知渠道，用户可在通知中心查看审核结果
- **FR-010**: 系统必须允许管理员配置启用的通知渠道（邮件、应用内、或两者同时）
- **FR-011**: 审核批准时，系统必须向提交人发送包含文件信息和审核意见的通知
- **FR-012**: 审核拒绝时，系统必须向提交人发送包含文件信息、拒绝理由的通知
- **FR-013**: 通知发送失败时，系统必须记录错误日志，并支持重试机制

#### 单元测试覆盖增强

- **FR-014**: 系统必须为 fileService 编写单元测试，覆盖所有业务逻辑方法
- **FR-015**: 系统必须为 reviewService 编写单元测试，覆盖所有业务逻辑方法
- **FR-016**: 系统必须为 gitService 编写单元测试，覆盖所有业务逻辑方法
- **FR-017**: 系统必须为 dependencyService 编写单元测试，覆盖所有业务逻辑方法
- **FR-018**: 系统必须为 consistencyService 编写单元测试，覆盖所有业务逻辑方法
- **FR-019**: 每个服务模块的单元测试覆盖率必须不低于 80%
- **FR-020**: 整体核心业务逻辑的单元测试覆盖率必须不低于 80%
- **FR-021**: 单元测试必须包含正常场景、边界条件和错误处理场景

### 关键实体

- **OpenAPI 引用错误**: 表示 OpenAPI 文档中的引用路径错误，包含错误的引用位置（文件和行号）、错误的引用路径、正确的引用路径
- **任务编号记录**: 表示任务列表中的编号历史，包含任务描述、旧编号、新编号、修改原因
- **通知配置**: 表示系统的通知渠道配置，包含渠道类型（邮件/应用内）、启用状态、配置参数（如 SMTP 服务器地址）
- **通知记录**: 表示发送的通知历史，包含通知 ID、接收人、通知类型（批准/拒绝）、发送渠道、发送状态、发送时间、失败原因（如果失败）
- **测试覆盖率报告**: 表示服务模块的测试覆盖率统计，包含服务名称、测试用例数量、通过数量、失败数量、覆盖率百分比、未覆盖代码行列表

## 成功标准 *(必填)*

### 可衡量的成果

- **SC-001**: OpenAPI 验证工具对 contracts/api.yaml 的检查结果为零错误
- **SC-002**: 任务列表中不存在重复的任务描述和职责
- **SC-003**: 任务编号从 T001 到最后一个任务号连续无跳过
- **SC-004**: 5 个服务模块（fileService、reviewService、gitService、dependencyService、consistencyService）的单元测试覆盖率均达到 80% 以上
- **SC-005**: 整体核心业务逻辑的单元测试覆盖率不低于 80%
- **SC-006**: 审核结果通知在审核操作完成后 30 秒内发送给提交人
- **SC-007**: 技术团队可以在 15 分钟内完成所有规格质量修正任务
- **SC-008**: 修正后的规格文档能够通过所有验证工具的检查，无警告和错误

## 假设

- OpenAPI 文档修正仅涉及引用路径错误，不需要重新设计 API 结构
- 任务重新编号不会影响已标记为完成的任务（使用复选标记）
- 邮件通知使用系统配置的 SMTP 服务器，应用内通知存储在数据库中
- 单元测试覆盖率计算包含测试的代码行数，排除注释和空行
- 服务模块的业务逻辑主要在 Service 层，不包括简单的 CRUD 数据库操作（这些由数据访问层测试覆盖）
- 通知失败重试最多执行 3 次，间隔为 1 分钟
- 测试覆盖率工具使用 Jest 内置的覆盖率功能（nyc/istanbul）
