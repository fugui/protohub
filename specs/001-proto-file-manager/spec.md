# 功能规格说明: Proto 文件管理系统

**功能分支**: `001-proto-file-manager`
**创建日期**: 2026-01-31
**状态**: 草稿
**输入描述**: "我想开发一个 protobuf Interface 的 proto 文件的管理系统， 进行文件的注册、修改的审核流程， 并在流程中自动进行一些基本的检查， 包括基本的命名规范、常用词汇的名称规范、抽取公共接口等， 并在界面上展现各个子系统间的依赖关系等。"

## 用户场景与测试 *(必填)*

### 用户故事 1 - Proto 文件注册与初步管理 (优先级: P1)

开发人员创建并提交新的 proto 文件到系统，系统自动解析文件内容并存储。

**为什么是此优先级**: 这是系统的核心功能，其他所有功能都依赖于此。用户需要能够注册和管理 proto 文件才能进行后续的审核、检查和依赖分析。

**独立测试**: 可以通过注册一个 proto 文件、查看文件列表、编辑和删除文件来独立测试完整的价值交付。

**验收场景**:

1. **给定** 用户已登录系统，**当** 用户上传一个新的 proto 文件，**那么** 系统成功解析文件内容并显示在文件列表中
2. **给定** 文件列表中已有 proto 文件，**当** 用户点击某个文件，**那么** 系统显示该文件的详细内容和元数据
3. **给定** 用户正在查看 proto 文件详情，**当** 用户编辑文件内容并保存，**那么** 系统更新文件并记录版本信息
4. **给定** 用户想要删除 proto 文件，**当** 用户确认删除操作，**那么** 系统移除该文件及相关元数据
5. **给定** 上传的 proto 文件格式不正确，**当** 系统解析失败，**那么** 系统显示具体的错误信息并拒绝上传
6. **给定** 用户已配置 Git 仓库信息，**当** 用户选择从 Git 仓库导入 proto 文件，**那么** 系统连接到 Git 仓库并拉取指定的 proto 文件
7. **给定** 用户执行 Git 仓库导入，**当** 导入过程中 Git 仓库连接失败，**那么** 系统显示错误信息并允许用户重试
8. **给定** 用户选择检查 Git 仓库与本地文件一致性，**当** 系统完成对比检查，**那么** 系统显示所有存在差异的文件列表及具体差异内容

---

### 用户故事 2 - 审核流程管理 (优先级: P2)

管理员对提交的 proto 文件进行审核，可以批准或拒绝文件变更，并记录审核意见。

**为什么是此优先级**: 审核流程确保接口规范的统一性和质量控制，是团队协作中的重要环节。在文件注册之后需要建立审核机制。

**独立测试**: 可以通过提交文件修改请求、审核员查看待审核列表、批准或拒绝变更来独立测试审核流程的完整价值。

**验收场景**:

1. **给定** 开发人员提交了文件修改请求，**当** 审核员进入审核工作台，**那么** 系统显示所有待审核的变更列表
2. **给定** 审核员正在查看某个审核请求，**当** 审核员批准该请求，**那么** 文件变更正式生效并通知提交人
3. **给定** 审核员正在查看某个审核请求，**当** 审核员拒绝该请求并填写拒绝理由，**那么** 文件保持原状态并通知提交人拒绝原因
4. **给定** 审核员批准了文件变更，**当** 提交人查看审核历史，**那么** 系统显示完整的审核记录和审核意见
5. **给定** 审核请求已经被处理，**当** 另一个审核员尝试操作，**那么** 系统提示该请求已被处理

---

### 用户故事 3 - 自动检查规则 (优先级: P2)

系统在文件注册和修改时自动执行命名规范检查、常用词汇规范检查和公共接口抽取建议。

**为什么是此优先级**: 自动检查是提高接口质量和减少人工审查成本的关键功能。在审核之前进行自动检查可以帮助开发人员提前发现和修复问题。

**独立测试**: 可以上传不符合规范的 proto 文件，查看系统自动生成的检查报告和修改建议，独立验证自动检查功能的价值。

**验收场景**:

1. **给定** 用户上传了一个命名不符合规范的 proto 文件，**当** 系统完成检查，**那么** 系统显示所有命名规范违规项及修改建议
2. **给定** 文件中使用了非标准的常用词汇，**当** 系统执行词汇规范检查，**那么** 系统标记非标准词汇并提供标准词汇建议
3. **给定** 多个文件中存在重复的消息定义，**当** 系统执行公共接口抽取检查，**那么** 系统建议将重复定义抽取为公共接口
4. **给定** 用户查看检查报告，**当** 用户点击某个检查项，**那么** 系统高亮显示相关代码位置和详细说明
5. **给定** 所有自动检查项都通过，**当** 系统完成检查，**那么** 系统显示"检查通过"并允许进入审核流程

---

### 用户故事 4 - 依赖关系可视化 (优先级: P3)

用户在界面上查看各子系统间的接口依赖关系图，了解接口使用情况和影响范围。

**为什么是此优先级**: 依赖关系可视化是高级分析功能，帮助团队理解系统架构和进行变更影响分析。虽然重要，但不是 MVP 的必需功能。

**独立测试**: 可以上传多个相关的 proto 文件，查看系统生成的依赖关系图，验证依赖关系的准确性和可视化效果。

**验收场景**:

1. **给定** 系统中已注册多个 proto 文件，**当** 用户访问依赖关系图页面，**那么** 系统显示各子系统间的接口依赖拓扑图
2. **给定** 用户正在查看依赖关系图，**当** 用户点击某个节点（子系统），**那么** 系统高亮显示该节点的所有依赖和被依赖关系
3. **给定** 用户需要了解接口变更的影响范围，**当** 用户选择某个 proto 文件，**那么** 系统标记所有依赖该接口的子系统
4. **给定** 依赖关系图中存在循环依赖，**当** 系统检测到循环依赖，**那么** 系统用红色高亮显示循环路径
5. **给定** 用户需要导出依赖关系图，**当** 用户点击导出按钮，**那么** 系统生成可下载的图片文件（PNG 或 SVG 格式）

### 边界情况

- 系统如何处理超大 proto 文件（超过 10MB）？
- 当多个用户同时编辑同一个文件时如何处理冲突？
- 审核员在审核过程中文件被修改了怎么办？

### 关键实体

- **用户**: 表示系统用户，包含用户名、邮箱、角色（开发者、审核员、管理员）、创建时间等属性
- **Git 仓库配置**: 表示 Git 仓库连接配置，包含仓库 URL、分支名称、认证凭据、最后同步时间等属性
- **Proto 文件**: 表示注册的 proto 文件，包含文件名、文件内容、包名、所属子系统、创建人、创建时间、当前状态（草稿、待审核、已批准、已拒绝）、当前版本号、关联的 Git 仓库 ID（如果有）、锁定状态（是否被锁定）、锁定用户（如果有）、锁定时间等属性
- **文件版本**: 表示 proto 文件的某个历史版本，包含版本号、文件内容、修改人、修改时间、变更说明等属性，与 Proto 文件是多对一关系
- **审核记录**: 表示一次文件变更审核，包含文件 ID、提交人、提交时间、审核人、审核时间、审核状态（待审核、已批准、已拒绝）、审核意见等属性
- **检查报告**: 表示对 proto 文件执行自动检查的结果，包含文件 ID、检查时间、违规项列表、建议列表等属性
- **违规项**: 表示检查发现的单个违规，包含检查规则类型、违规位置、违规描述、建议修改方式等属性
- **依赖关系**: 表示 proto 文件间的依赖，包含源文件 ID、目标文件 ID、依赖类型（import）、创建时间等属性
- **子系统**: 表示业务子系统，包含子系统名称、描述、创建时间、负责人等属性，与 Proto 文件是一对多关系

## 假设

- 系统使用内部用户账户体系，暂不集成第三方认证
- Git 仓库认证支持 HTTPS 和 SSH 两种方式，凭据以明文形式存储在数据库中，所有有权限的用户可见（适用于开发测试环境）
- Git 仓库导入采用一次性拉取操作，不支持实时同步或 webhook 自动触发
- 常用词汇规范字典由管理员手动维护，初期提供默认词汇表
- 审核流程采用串行审核（一次只有一个审核员处理），暂不支持并行审核
- 文件编辑采用悲观锁机制，同一时间只有一个用户可以编辑特定文件，锁在保存或取消编辑时自动释放
- 审核过程中如果文件被修改（如管理员强制解锁后修改），审核流程继续按当前状态完成，不做特殊处理
- 依赖关系图主要关注 proto 文件级别的依赖，暂不细化到字段级别的依赖
- 检查规则的可配置性限制在管理员层面，普通用户无法修改检查规则
- 删除文件时必须先检查依赖关系，若存在引用则阻止删除并提示用户先解除依赖
